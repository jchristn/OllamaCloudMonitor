# Internationalization

English is the source and fallback language. All twelve baseline languages in the shared requirements are available before and after login, along with expansion and RTL pseudo-locales.

`dashboard/src/i18n/localeRegistry.js` is the central registry: BCP 47 code, English name, autonym, direction, fallback and optional script/font notes. The initial Portuguese translation uses Brazilian terminology; all Portuguese browser variants resolve to pt-BR. The Chinese translation uses Simplified Chinese; Chinese browser variants resolve to zh-Hans, including browsers requesting Traditional Chinese because no Traditional catalog is supplied. The selected locale is displayed explicitly rather than claiming a separate regional translation. Other regional tags such as fr-CA, de-DE and hi-IN resolve to their supported base language. Legacy `pt`/`zh` preferences and the `Kanji` alias resolve to pt-BR, zh-Hans and ja respectively. Pseudo-locale codes remain distinct.

The preference order is explicit selection, persisted `monitor.locale`, browser preferences, then English. No profile preference exists. Direction and root `lang` update centrally on language changes; logout preserves the preference. Number, currency, percentage and UTC date/time formatting receives the active locale explicitly. Installed system font stacks cover CJK, Arabic shaping and Devanagari without contacting font services.

## Catalogs and loading

Each language has a UTF-8 JSON catalog under `dashboard/src/i18n/locales/`. English ships in the main bundle as a reliable fallback. i18next loads the selected non-English catalog through a Vite-generated dynamic import; other languages are fetched only when selected. The app waits for initial locale setup before rendering meaningful UI, preventing an English flash for a stored or browser-selected language. The current application has one `translation` namespace; the loader interface supports a namespace-aware backend if the app grows.

The existing message identifiers remain stable when adding languages. Messages use i18next interpolation (`{{amount}}`, `{{seconds}}`); preserve those placeholders exactly. Do not concatenate translated fragments around grammatical variables. Labels, accessible names, loading/error states and notices use the same catalogs. Stable server error codes are mapped in the client; upstream error bodies are not displayed.

Technical identifiers (model names, URLs, HTTP methods, JSON keys, operation names, product names, versions, wire parameters and UTC) are intentionally unchanged. Language names are autonyms in the registry, not translated by the active catalog. Translations cover login, configured-account access, navigation, usage, credits, models, charts, tables, settings, and the API explorer.

## Maintenance and checks

To add a locale, add a complete catalog and its registry entry, including English name, autonym, direction, fallback and any script notes. No page logic or loader mapping changes are needed. Add browser smoke coverage and document any regional/script policy. Review translations with a native speaker before wider distribution, especially financial terminology and security/access notices.

Run `npm test --prefix dashboard`. Unit checks cover key and interpolation parity, locale metadata, canonical codes, regional aliases and formatting across all twelve real languages. `npm run check:i18n --prefix dashboard` also detects missing/orphaned keys, encoding problems, hard-coded JSX text outside approved technical labels, and disagreement between registry and catalog files. These checks run in CI.

Browser tests cover every language through login, reload, authenticated navigation, mobile models/explorer/settings, and logout. They verify language persistence, root lang/dir, responsive overflow, equal explorer control heights, browser-language detection and stored-preference precedence. A delayed catalog test verifies that the first render waits for the selected language and that switching languages requests only the selected catalog. Expansion and bidi pseudo-locales remain covered.

Glossary: “usage” means consumed activity, “balance” means currently available credit, “included” means plan allowance, and “purchased” means unexpired bought credits. Cached input is already part of input tokens. Translators must preserve the distinction between current account-wide balance and model-filtered usage, and between unknown legacy amounts and zero.
